Извлечение именованных сущностей локальными языковыми моделями¶

Проверим, можно ли использовать готовую локальную LLM для NER без обучения. Сравним Qwen 3 4B и более компактную Gemma 3 1B, исходную и уточнённую инструкции, группировку по типам и список в порядке появления.

Демонстрационный ноутбук local_llm_ollama_demo.ipynb изучен. Данные уже скачаны из tner/conll2003. Обрабатываем 100 предложений из train. Эталон используется только для оценки. Облачные варианты исследуем по документации: запросы с корпусом в облако не отправляем.

def token_offsets(tokens):
    starts, ends, position = [], [], 0
    for token in tokens:
        starts.append(position)
        position += len(token)
        ends.append(position)
        position += 1
    return starts, ends

def bio_to_entities(tokens, tags):
    starts, ends = token_offsets(tokens)
    entities, active, begin = [], None, 0
    labels = [id2label[tag] for tag in tags] + ["O"]
    for i, label in enumerate(labels):
        prefix, kind = label.split("-", 1) if label != "O" else ("O", None)
        if prefix == "I" and kind != active:
            raise ValueError(f"Некорректное продолжение BIO: {i}, {label}")
        if active and (prefix != "I" or kind != active):
            entities.append({"text": " ".join(tokens[begin:i]), "type": active,
                             "start": starts[begin], "end": ends[i - 1],
                             "token_start": begin, "token_end": i})
            active = None
        if prefix == "B":
            active, begin = kind, i
    return entities

def make_request(text, model, prompt, format_name):
    format_instruction = (GROUP_INSTRUCTION if format_name == "grouped"
                          else ORDER_INSTRUCTION)
    schema = SCHEMAS[format_name].model_json_schema()
    content = (prompt + "\n" + format_instruction + "\nJSON Schema:\n"

    return {"model": model, "messages": [{"role": "user", "content": content}],

def run_experiment(name, model, prompt, format_name):
    records, cached = [], 0
    for position, item in enumerate(inputs, 1):
        request = make_request(item["text"], model, prompt, format_name)
        path = response_path(request, item["id"])
        if path.exists() and not REFRESH_RESPONSES:
            record = json.loads(path.read_text(encoding="utf-8"))
            assert record["request"] == request
            cached += 1
        else:
            record = generate_one(request, item)
            save_json(path.with_suffix(".tmp"), record)
            path.with_suffix(".tmp").replace(path)
        records.append({**record, "experiment": name, "format": format_name})
        if position % 10 == 0:
            print(f"{name}: {position}/{len(inputs)}", flush=True)
    save_json(RESULTS / f"{name}.json", records)
    if cached < len(records):
        save_json(RESULTS / f"{name}_resident.json", client.get("/api/ps").json())
    print(f"Из кэша: {cached}; новых запросов: {len(records) - cached}.")
    return records

5. Строгая оценка сущностей¶

Основные метрики — entity-level Precision, Recall и micro-F1. TP требует полного совпадения границ упоминания и типа. Лишние упоминания — FP, пропущенные — FN. Ошибочный тип даёт один FP и один FN. Macro-F1 и F1 по типам помогают увидеть ошибки редкой MISC, которые скрывает усреднение по всем сущностям. Дополнительно считаем долю полностью правильных предложений, корректность структуры, незаземлённые фрагменты, повторы и нарушение порядка. Строгое совпадение полного фрагмента соответствует принципу оценки в описании CoNLL-2003.

Строки ответа сопоставляем с точными непрерывными фрагментами исходного текста на границах токенов. Повторные одинаковые строки связываем с ещё не использованным вхождением слева направо в пределах того же типа; эталон при этом не используется. Если модель назначает одному фрагменту несколько типов, все предсказания оцениваем, сохраняя правильный TP и учитывая лишний тип как FP. Повторы сверх числа вхождений тоже дают FP. Такие конфликты отмечаем отдельно. Схема без offsets не позволяет однозначно определить, какое из одинаковых вхождений пропущено. Это ограничение обоих исследуемых форматов, а не основание угадывать по gold.

ungrounded означает отсутствие точного фрагмента на границах токенов. Строка может встречаться внутри токена (Australian в league-Australian) и всё равно не соответствовать размеченному фрагменту. Такие случаи отделяем от полностью отсутствующих строк в диагностике ошибок.

def parse_response(record):
    raw = record.get("response", {}).get("message", {}).get("content", "")
    if record.get("transport_error"):
        return [], False, record["transport_error"]
    if record.get("response", {}).get("done_reason") == "length":
        return [], False, "Ответ оборван по лимиту генерации"
    try:
        parsed = SCHEMAS[record["format"]].model_validate_json(raw)
        if record["format"] == "ordered":
            entities = [item.model_dump() for item in parsed.entities]
        else:
            entities = [{"text": text, "type": kind} for kind in TYPES
                        for text in getattr(parsed.entities, kind)]
        return entities, True, ""
    except ValidationError as error:
        return [], False, str(error).splitlines()[0]

def align_entities(entities, text):
    aligned, used, seen_spans = [], set(), set()
    for index, entity in enumerate(entities):
        pattern = r"(?<!\S)" + re.escape(entity["text"]) + r"(?!\S)"
        candidates = [(match.start(), match.end())
                      for match in re.finditer(pattern, text)]
        available = [span for span in candidates if (*span, entity["type"]) not in used]
        span = (available or candidates or [(-index - 1, -index - 1)])[0]
        duplicate = bool(candidates) and span in seen_spans
        if candidates:
            used.add((*span, entity["type"]))
            seen_spans.add(span)
        aligned.append({**entity, "start": span[0], "end": span[1],
                        "grounded": bool(candidates), "duplicate": duplicate,
                        "substring_present": entity["text"] in text})
    return aligned

def prf(tp, fp, fn):
    precision = tp / (tp + fp) if tp + fp else 0.0
    recall = tp / (tp + fn) if tp + fn else 0.0
    f1 = 2 * tp / (2 * tp + fp + fn) if 2 * tp + fp + fn else 0.0
    return {"precision": precision, "recall": recall, "f1": f1}

def score_one(record):
    entities, valid, validation_error = parse_response(record)
    predicted = align_entities(entities, input_by_id[record["id"]]["text"])
    expected = gold_by_id[record["id"]]
    p, g = Counter(map(entity_key, predicted)), Counter(map(entity_key, expected))
    tp, fp, fn = sum((p & g).values()), sum((p - g).values()), sum((g - p).values())
    positions = [item["start"] for item in predicted]
    ordered_eligible = record["format"] == "ordered" and len(predicted) >= 2
    checkable = all(item["grounded"] for item in predicted)
    order_ok = (checkable
                and all(a < b for a, b in zip(positions, positions[1:])))
    return {"id": record["id"], "split": record["split"],
            "experiment": record["experiment"], "tp": tp, "fp": fp, "fn": fn,
            "valid": valid, "validation_error": validation_error,
            "exact": valid and p == g, "ordered_eligible": ordered_eligible,
            "order_ok": order_ok, "sequence_exact": valid and
            list(map(entity_key, predicted)) == list(map(entity_key, expected)),
            "order_checkable": checkable,
            "predicted": predicted, "gold": expected, "wall_s": record["wall_s"],
            "ungrounded": sum(not item["grounded"] for item in predicted),
            "duplicates": sum(item["duplicate"] for item in predicted)}

def summarize(scored, partition):
    rows = [row for row in scored if partition == "all" or row["split"] == partition]
    tp, fp, fn = [sum(row[key] for row in rows) for key in ["tp", "fp", "fn"]]
    eligible = [row for row in rows if row["ordered_eligible"]]
    return {"split": partition, "n": len(rows), "tp": tp, "fp": fp, "fn": fn,
            **prf(tp, fp, fn), "valid_rate": np.mean([row["valid"] for row in rows]),
            "sentence_exact": np.mean([row["exact"] for row in rows]),
            "order_n": len(eligible), "order_rate": np.mean(
                [row["order_ok"] for row in eligible]) if eligible else np.nan,
            "ungrounded": sum(row["ungrounded"] for row in rows),
            "duplicates": sum(row["duplicates"] for row in rows),
            "median_s": np.median([row["wall_s"] for row in rows])}

def scores_by_type(scored, partition="test"):
    rows, results = [row for row in scored if partition == "all" or row["split"] == partition], []
    for kind in TYPES:
        tp = fp = fn = 0
        for row in rows:
            p = Counter(entity_key(e) for e in row["predicted"] if e["type"] == kind)
            g = Counter(entity_key(e) for e in row["gold"] if e["type"] == kind)
            tp += sum((p & g).values())
            fp += sum((p - g).values())
            fn += sum((g - p).values())
        results.append({"type": kind, "support": tp + fn,
                        "tp": tp, "fp": fp, "fn": fn, **prf(tp, fp, fn)})
    return pd.DataFrame(results)

Поэтому рядом приведена доля полного совпадения последовательности с gold. Незаземлённые строки делают порядок непроверяемым и не засчитываются как успешный порядок.

Группировка удобна для списков людей, мест и организаций и агрегации по типам. Схема компактная, тип записывается один раз на группу, пустые группы задают предсказуемые ключи. Общий порядок между типами потерян; восстановление позиций по строкам неоднозначно при повторных упоминаниях.

Единый список удобен для последовательной обработки, подсветки, привязки сущностей к контексту и построения связей. Тип повторяется для каждого объекта, ответ может быть длиннее, а порядок приходится проверять программно. Для production в оба формата стоит добавить проверяемые start/end и идентификатор упоминания. Здесь offsets не выдаёт модель: такой третий формат потребовал бы отдельного эксперимента. Ни один из двух форматов сам по себе не устраняет смысловые ошибки NER.

def error_details(row):
    extra, missing = [], list(row["gold"])
    for predicted in row["predicted"]:
        match = next((e for e in missing if entity_key(e) == entity_key(predicted)), None)
        if match:
            missing.remove(match)
        else:
            extra.append(predicted)
    errors = []
    for predicted in extra:
        same = next((e for e in missing if entity_key(e, False) ==
                     entity_key(predicted, False)), None)
        overlap = next((e for e in missing if predicted["start"] >= 0 and
                        max(e["start"], predicted["start"]) <
                        min(e["end"], predicted["end"])), None)
        expected = same or overlap
        kind = ("wrong_type" if same else "boundary" if overlap else
                "duplicate" if predicted["duplicate"] else
                "token_boundary" if not predicted["grounded"] and predicted["substring_present"]
                else "ungrounded" if not predicted["grounded"] else "extra")
        if expected:
            missing.remove(expected)
        errors.append({"kind": kind, "prediction": predicted, "gold": expected})
    errors.extend({"kind": "missing", "prediction": None, "gold": e} for e in missing)
    return errors

def paired_f1_delta(left_name, right_name):
    left = [row for row in all_scored[left_name] if row["split"] == "test"]
    right = [row for row in all_scored[right_name] if row["split"] == "test"]
    assert [row["id"] for row in left] == [row["id"] for row in right]
    a = np.array([[row[key] for key in ["tp", "fp", "fn"]] for row in left])
    b = np.array([[row[key] for key in ["tp", "fp", "fn"]] for row in right])
    rng, deltas = np.random.default_rng(SEED), []
    for _ in range(BOOTSTRAP_SAMPLES):
        ids = rng.integers(0, len(a), len(a))
        deltas.append(prf(*b[ids].sum(axis=0))["f1"] - prf(*a[ids].sum(axis=0))["f1"])
    low, high = np.quantile(deltas, [.025, .975])
    return {"left": left_name, "right": right_name, "low": low, "high": high,
            "delta": prf(*b.sum(axis=0))["f1"] - prf(*a.sum(axis=0))["f1"]}

Расчёт относится к одному проходу по 100 предложениям, а не ко всем пяти локальным вариантам. Для повторения всей серии входы, выходы и расходы нужно суммировать по всем вариантам; бесплатный дневной лимит может потребовать нескольких дней. На бесплатном Gemini вне ЕЭЗ, Швейцарии и Великобритании входы и ответы могут использоваться для улучшения продуктов, включая обработку людьми. В указанных регионах действуют условия обработки платного сервиса даже для бесплатного использования. Платный Gemini не использует входы и ответы для улучшения продуктов, но предусматривает ограниченное хранение для контроля нарушений. См. условия Gemini.

Groq запрещает обучение на входах и ответах без явного разрешения клиента (соглашение). При обычном inference данные по умолчанию не сохраняются; возможны логи надёжности/злоупотреблений до 30 дней. Есть настройка ZDR; batch хранит файлы до 30 дней. См. обработку данных Groq.

Нужны учётная запись и API-ключ, соблюдение условий датасета и доступность сервиса в регионе. Для Gemini нужно свериться со списком регионов: доступ нельзя считать универсальным. В данном исследовании аккаунты не создавали, ключи не использовали и фактическую доступность API не проверяли.

Облако практичнее для небольших нерегулярных партий при доступном API, разрешённой передаче данных и ограниченном локальном оборудовании. Бесплатный тариф удобен для пилота, но квоты, очереди, смена моделей и условия обработки данных делают его слабой гарантией для production. Для стабильной нагрузки следует оценивать платный API и обработку ошибок 429 с backoff. Локальная модель удобнее для работы без сети, контроля версии и места обработки. Высокое облачное качество здесь не доказано: облачные модели потребуют той же оценки NER и MISC на размеченных текстах.

13. Выводы и ограничения¶

Среди исследованных конфигураций для прототипа выбираем Qwen 3 4B Instruct с уточнённой инструкцией и единым списком. Выбор сделан по dev (F1 = 0,636); на test Precision = 0,658, Recall = 0,570, F1 = 0,611. На всех 100 предложениях описательный F1 = 0,618. Один проход занял 18,8 мин; медиана запроса — 5,34 с, p95 — 28,62 с. Оценка занятого моделью объёма Ollama — 3,26 GiB, CPU-режим. Список уменьшил лишние сущности, но часть полноты была потеряна, а порядок требует отдельной проверки.

Gemma 3 1B уменьшила этот объём до 1,12 GiB, однако test F1 составил 0,305 при группировке и 0,271 при списке, а медианы — 14,65 и 14,87 с. В этих условиях сопоставимого качества или выигрыша по времени не получено; меньшее число параметров само по себе не гарантирует меньшую задержку. Это сравнение конкретных семейств, инструкции и реализации в Docker.

Для полностью автоматического извлечения всех четырёх типов качество недостаточно: у выбранного варианта только 7 из 62 непустых test-предложений полностью совпали с gold; F1 MISC = 0,171. PER заметно лучше (F1 = 0,894), но результат нельзя переносить на документы компании без новой оценки. Модель можно использовать как помощника для разметки с проверкой человеком. В программной системе нужны Pydantic-валидация, проверка фрагментов по тексту, контроль дублей, конфликтующих типов и порядка, а также явная обработка обрыва ответа. Эти проверки не заменяют оценку смысловой правильности.

Облачный API может быть практичнее для небольших нерегулярных партий при доступности в регионе и допустимых условиях обработки данных: расчётная стоимость одного прохода очень мала. Его качество NER здесь не измерено. Локальный вариант сохраняет контроль над данными и версией модели и работает без сети после загрузки весов. Схема задаёт интерфейс результата; правильность сущностей определяется моделью, инструкцией, контекстом и принятой разметкой.

100 предложений — небольшая случайная выборка англоязычных новостей и спортивных/финансовых строк CoNLL. В ней нет русскоязычных текстов и документов компании; результаты на них могут отличаться. Редкая MISC имеет мало примеров. Внутренние dev/test взяты из train, возможны общие статьи и попадание известного публичного корпуса в предобучение LLM. Изоляция предложений лишает модель контекста.

BIO — эталон выбранного корпуса, а не универсальная истина. Встречаются спорные типы, непоследовательные границы и названия без разметки. Мы не меняли gold по ответам модели. Строгое сравнение чувствительно к восстановлению пробелов. Результат без offsets неоднозначен для одинаковых повторных упоминаний.

Измерения относятся к двум квантованным моделям, заданной инструкции, одному seed, CPU Docker, четырём потокам и конкретной версии Ollama. Один запрос на предложение не измеряет вариативность ответов и нагрузку с конкуренцией. Температура 0 уменьшает случайность, но не гарантирует идентичность на другом оборудовании. Bootstrap оценивает только вариативность этой выборки и не учитывает зависимость предложений внутри статей. Нет сравнения с обученной NER, нет испытания prompt injection, длинных документов и отказов production.

Тарифы, квоты и модели облачных сервисов меняются. Расчёт стоимости приблизителен, не включает электричество, амортизацию, разработку и эксплуатацию локального сервиса. Гарантия схемы не заменяет проверку качества и правила обработки недостоверных предсказаний в программной системе.

Уточнённая инструкция выведена по dev Qwen и перенесена в Gemma без отдельной настройки под её семейство. Сравниваем эти общие условия, а не максимальное достижимое качество каждой модели. Последовательные проходы не контролируют весь фоновый шум системы; длина ответов и повторное использование общего префикса Ollama также влияют на время. В gold нет повторов одинакового полного упоминания внутри предложения: такие повторы проверены только синтетически. У трёх gold-строк (Bistrita, California, Israel) есть несколько буквальных позиций, в том числе внутри более длинного названия. Восстановление позиций слева направо здесь является соглашением оценивания, а не ответом модели.
